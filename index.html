编排是代码，
LLM 只做单环节

agent-harness 是多智能体编排的通用内核。 它只提供确定性编排的机制面——报告协议、工具判定环、续跑契约、 上下文预算、执行沙箱——不认识任何领域概念。

运维词表、专家包、诊断链、拓扑内容、品牌文案都不属于本仓： 那是宿主的资产。内核只给机制与判据，宿主只给内容与拓扑。

为什么内核不该知道自己在给谁干活

判定口诀只有一句：「这个包需要知道自己在给谁干活吗？」需要，就属于宿主。

领域知识渗回是必然的

拆完之后最现实的风险不是拆不动，而是业务代码一年年渗回内核，等发现时 harness 已退化成「换了个名字的 monolith」。

所以边界不写在散文里——它写成了 8 条规则 + 5 条 go/ast 结构规则。

判定语义必须跨宿主一致

失败分类、隔离档位、提交闸的判定若各宿主各写一套，必然漂移到没人发现为止。 组合逻辑归内核，判定归各自机制。

因此门禁执行体是可导入包：宿主复用同一份判据，不必各写一遍。

门禁自身也要能被检查

规则的失败形态必须是变红，不是变绿。改任何判定逻辑， 必须同时给「坏实现会红」的用例。

「从没见过它触发的规则」等于没有规则——每条规则都做过反向验证。

边界

本仓有什么、没有什么——这条线由机器判，不由 review 判。

✓ 有（机制，与领域无关）

  • protocol 统一报告协议 + 五级容错解析 + 白名单校验
  • contract / statemachine 编排运行契约与环节状态机
  • tooldisclose / guardset / toolfail 工具判定环
  • checkpoint / commitgate 续跑契约与终态独占提交闸
  • budget / offload / spill 上下文三件套
  • netguard / pii 出站守卫与个人信息脱敏
  • ptc / sandbox 程序化工具编排与执行沙箱
  • sideeffect / retryplan 副作用至多一次与重试处置
  • taskboard / skilldisclose / hookengine 协调与披露面

✗ 没有（资产，属于宿主）

  • 专家包 / 专家清单 / 技能
  • 诊断链 / 编排图（拓扑内容）
  • 运维词表（巡检域、集群词面…）
  • 目标类型（主机 / 集群 / Pod）
  • 审批风险分级与幂等键的存储实现
  • 事件持久化与表结构
  • IM 通道 / 通知模板 / 品牌文案
  • 工具实现（MCP server）

特性

不是「我们支持什么」，是「我们把哪些坑变成了机制」。

工具调用只有一条路

渐进披露、披露门、多守卫合成、失败分类、程序内调用——全部接成同一条判定环。 包括模型自己写的程序里的工具调用，也一样过。

普通工具调用 ─┐
             ├─→ invoke.Stage 链 ─→ guardset ─→ tooldisclose
ptc 程序内   ─┘                   └─→ policy ─→ dispatch

少接一段，那个位置就成了整条链上唯一绕过所有门禁的路径。

崩了能接着跑

恢复判定做成纯函数而不是留给宿主临场决定——临场决定必然选最坏的那个。 三条硬规则：可信边界按依赖判定、终态不自动重开、序号单调闸。

并且不会「两条分支都赢了」：终态独占权单独一道闸，放闸靠凭证而非内容比对。

上下文是有限预算

budget 管输入侧分段计量（区分「工具面膨胀」与「历史膨胀」）， offload 管大对象外置（两阶段：首次只标记）， spill 管输出侧截断与分页取回。

失败是数据表

toolfail 把「类别 → 可重试性 / 退避 / 需人工 / 重发安全 / 模型指引」 做成数据表而非散落的 if。不可归类一律不可重试。

重发安全与重试价值是两个正交维度：超时值得重试，但服务端可能已执行。

N 轮 ReAct 往返塌缩成 1 轮

ptc 让模型写程序、沙箱执行、只把归并后的小结果带回上下文： 原始数据不过模型面。三重预算（墙钟 / 调用数 / 字节数）替代 OS 沙盘， 纯 Go 零 CGO。

派生状态只有一个真相

任何「代次 / 版本 / 序号」只允许有一个真相。需要额外视图时，让它是真相的投影， 不要另开一个计数器——两个计数器在并发下必然漂移。

边界不是文档，是门禁

「内核不许长出领域知识」写在散文里就会烂掉。这里它是机器判据， 全部挂在 make check 上，CI 只执行这一条。

8 条规则

  • harness-no-domain-vocabulary 领域词污染
  • harness-test-fixture-domain-vocabulary 夹具须用合成数据
  • harness-no-host-dependency 不得 import 宿主仓
  • harness-no-domain-runtime-deps 不得引入宿主运行时
  • harness-no-bare-goroutine 禁裸 go func
  • harness-no-printf-log-callback 禁 printf 回调焊进 API
  • harness-single-errors-package 全仓一套 errors
  • harness-sandbox-execution-single-entry 沙箱后端单入口

5 条 go/ast 结构规则

  • harness-facade-stays-facade 门包不许长出实现
  • harness-module-dependency-direction 包间依赖方向
  • 沙箱档位登记（档位声明要有人签字）
  • 执行路径不得绕过沙箱登记簿
  • 子进程出口登记

结构性判定走语法树，不走逐行正则——import 声明有六种以上书写形态。

提交前门禁全链

  • fmt · vet · lint · test
  • cover-gate（全局 60% + 逐包下限 70%）
  • govulncheck（依赖与标准库漏洞）
  • -race（竞态检测）
  • crossbuild（四平台交叉构建）
  • architecture-check（域词 + 依赖方向）
  • docsync（README ↔ 仓库事实一致）

门禁本体全在 make check 里，CI 只执行它——门禁不挂在工作流上变回「推送后门禁」。

门禁的失败形态必须是变红，不是变绿。

改任何判定逻辑，必须同时给「坏实现会红」的用例——只测「好实现能过」的用例， 一个把数字比较写成字符串比较的错实现照样全过。

sideeffect540oekit/pkg副作用「至多一次」的跨进程契约：幂等键（同一逻辑动作重试不重复施加）+ 租约（同一资源独占，带 TTL）+ 栅栏令牌（过期持有者的迟到写入被下游拒绝）+ 下游拒收契约（FencedSink：比较与写入须同一次原子操作，否则两个持有者会同时读到同一个旧值、双双通过检查，更旧的那次写入反而后落覆盖新的）。上游三个判据共用一次原子操作（Store.Acquire）——拆成三份存储就会出现「租约过了但幂等没过」的夹缝，允许同一动作被施加两次。执行失败不记账（没做成的不能记成做成了），但释放闸（否则失败残留的闸会把后续重试全挡成「别人占着」）。施加前有资格检查（ExecuteWith 两段式：准备 → 检查 → 施加）——闸已易主时根本不施加，因为 Complete 被拒只说明没记上账，副作用早已生效，事后补救不了。承诺的是至多一次而非 exactly-once——后者要求下游也接受幂等键
sidetest436oekit/pkgsideeffect.Store 的共享契约测试套件：宿主写完存储实现后跑一遍，违反哪条契约就红在哪一条——免得「各写一遍必然各判一套，漂移到没人发现为止」。10 条子测试覆盖「只做一次 / 已完成优先于占用 / 未过期时争用 / 过期后接管 / 令牌单调 / 过期持有者不得记账 / 过期持有者不得放闸 / 释放不等于完成 / 续期延长且不换令牌 / 闸已易主后续期被拒」。范式沿用上游 cachetest / singleflighttest：硬失败不静默跳过（显式接入套件＝声明要满足契约，跳过等于把「没测过」伪装成「通过了」）。时钟可注入（ClockedStore），否则过期场景恒不触发，套件会变成一组空断言
cmdpolicy409oekit/pkg命令级判据：把判定面从「工具调用」向下延伸到工具内部实际执行的那条命令。此前边界停在工具名上——一次 exec 审批通过后，它内部跑的是 git status 还是 rm -rf / 没有任何机制面看得见，宿主只能靠正则黑名单兜，而黑名单在「写法与语义不一致」时必然失效。本包用前缀 token 规则（先分词再比 token，不随引号/转义/空白漂移）+ 三态裁决（allow/prompt/forbidden，与 toolgate 词表同义不另立口径）+ 规则自带样例（每条规则可带 Match/NotMatch，New 在加载期用真实判定路径跑一遍，不一致即报错——这是「从没见过它触发的规则等于没有规则」的机器化：规则会随命令名漂移，而漂移不会报错，只会静静地不再命中）。冲突口径确定性：前缀更长者胜 → 同长度取更严 → 同档取名字字典序最小。SplitCommands 单独存在是因为前缀判据的典型绕过：git status; rm -rf / 的前缀是 git，对整串只判一次就会让一条 git 的 allow 规则放行后半段
egress269oekit/pkg出口策略：三档（ModeUnrestricted < ModeProxy < ModeDenied，单调可比、零值即最松）+ 声明自检（Validate）+ 兑现判据（Env / Verify）+ 后端能力问询（SatisfiedBy）。本包不含代理本体（那是上游 guardx 与宿主的活），只回答此前没人回答的三件事：这次执行要求哪一档出口 / 宿主给的环境是否真的兑现了那一档 / 某个沙箱后端能不能兑现它。两条底线都是「沉默与伪造都落在安全的那一侧」：后端不声明就按最弱处理（不是「没说不支持」＝满足，否则从没实现过出口控制的后端会被选中，声明与实际之间的落差没有信号）；禁网档拒绝伪造（ModeDenied 的 Env/Verify 直接报错，不做「尽力而为」——假装禁网比明确拒绝更危险，报告会显示「已兑现」而网络其实通着）
gatecheck504oagentkit/guardx、oagentkit/toolgate、oekit/pkg审批层与沙箱层的联合判据：Codex 的两层安全模型是「沙箱强制 + 审批策略，两层都同意才放行」。上游 guardx/sandbox（档位×预算）与 toolgate/policy（审批裁决）各自完整但互不知情——「两层是否都同意」这个判定没有单点，落在各宿主手里必然漂移。本包只做合成（不重新实现任何一层，那会造成与上游并存的第二份真相）。判据顺序有意为之：审批已否 ⇒ 直接否（档位再高也不该执行）；需人审 ⇒ 优先于档位不足（人该在场，而不是让宿主去找后端——否则这次调用既没执行也没人管，静默丢失）；计划模式单列（只审不执行 ≠ 拒绝）。Managed 是受管后端（把真后端包起来）：判据不通过就不委派（副作用不会发生）——判据与执行不可分，否则「判过的后端 ≠ 实际跑的后端」又有了信号落差
preset230oekit/pkg命名权限预设：把「隔离档位 × 审批模式 × 出口策略」三件散参数收成一份具名、只读、加载期自检的组合（Preset{Name,Level,Mode,Egress,Unsafe,Justification}）。散参数的病不是难写，是改一处漏两处——档位调到 OS 级而出口忘开代理、审批放到 auto 而沙箱仍是进程内，组合出来的权限谁都没声明过。自检两条最关键：三面全松必须显式 Unsafe 且写理由（「全都放开」最容易在调试时临时出现、然后留下来）；语义相同的两个名字即报错——两个名字一份组合在配置里看起来是「两个选择」，真正的伤害在留痕：报告里出现两个名字，读者会以为执行过两种权限。Resolve 遇未登记名字报错而不降级（降级方向不可预测，可能更松，而「打错一个字就用上另一档权限」没有任何信号）。方向是 preset → gatecheck（高层组装件认识低层判据），gatecheck 不认识 preset
retryplan192oagentkit/guardx重试处置决策：把「该不该重试」（toolfail 判）与「重试会不会重复施加」（sideeffect 判）合成一条可执行结论——三档路径（不重试 / 原样重发 / 走幂等键重放）。与 guardset 同族：组合逻辑归内核，判定归各自机制（各宿主各写一遍组合逻辑，必然各判一套）。关键一档是「可重试但原样重发不安全」——toolfail 只说「先确认上一次是否已生效」，没说什么怎么做到，而这正是幂等键的活；故该档判为 PathReplayed（走幂等键）。关键取舍：没有幂等键就不许「猜着重试」（降级为不重试，而非原样重发赌一次）
