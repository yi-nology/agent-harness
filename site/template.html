编排是代码，
LLM 只做单环节

agent-harness 是多智能体编排的通用内核。 它只提供确定性编排的机制面——报告协议、工具判定环、续跑契约、 上下文预算、执行沙箱——不认识任何领域概念。

运维词表、专家包、诊断链、拓扑内容、品牌文案都不属于本仓： 那是宿主的资产。内核只给机制与判据，宿主只给内容与拓扑。

为什么内核不该知道自己在给谁干活

判定口诀只有一句：「这个包需要知道自己在给谁干活吗？」需要，就属于宿主。

领域知识渗回是必然的

拆完之后最现实的风险不是拆不动，而是业务代码一年年渗回内核，等发现时 harness 已退化成「换了个名字的 monolith」。

所以边界不写在散文里——它写成了 条规则 + 5 条 go/ast 结构规则。

判定语义必须跨宿主一致

失败分类、隔离档位、提交闸的判定若各宿主各写一套，必然漂移到没人发现为止。 组合逻辑归内核，判定归各自机制。

因此门禁执行体是可导入包：宿主复用同一份判据，不必各写一遍。

门禁自身也要能被检查

规则的失败形态必须是变红，不是变绿。改任何判定逻辑， 必须同时给「坏实现会红」的用例。

「从没见过它触发的规则」等于没有规则——每条规则都做过反向验证。

边界

本仓有什么、没有什么——这条线由机器判，不由 review 判。

✓ 有（机制，与领域无关）

  • protocol 统一报告协议 + 五级容错解析 + 白名单校验
  • contract / statemachine 编排运行契约与环节状态机
  • tooldisclose / guardset / toolfail 工具判定环
  • checkpoint / commitgate 续跑契约与终态独占提交闸
  • budget / offload / spill 上下文三件套
  • netguard / pii 出站守卫与个人信息脱敏
  • ptc / sandbox 程序化工具编排与执行沙箱
  • sideeffect / retryplan 副作用至多一次与重试处置
  • taskboard / skilldisclose / hookengine 协调与披露面

✗ 没有（资产，属于宿主）

  • 专家包 / 专家清单 / 技能
  • 诊断链 / 编排图（拓扑内容）
  • 运维词表（巡检域、集群词面…）
  • 目标类型（主机 / 集群 / Pod）
  • 审批风险分级与幂等键的存储实现
  • 事件持久化与表结构
  • IM 通道 / 通知模板 / 品牌文案
  • 工具实现（MCP server）

特性

不是「我们支持什么」，是「我们把哪些坑变成了机制」。

工具调用只有一条路

渐进披露、披露门、多守卫合成、失败分类、程序内调用——全部接成同一条判定环。 包括模型自己写的程序里的工具调用，也一样过。

普通工具调用 ─┐
             ├─→ invoke.Stage 链 ─→ guardset ─→ tooldisclose
ptc 程序内   ─┘                   └─→ policy ─→ dispatch

少接一段，那个位置就成了整条链上唯一绕过所有门禁的路径。

崩了能接着跑

恢复判定做成纯函数而不是留给宿主临场决定——临场决定必然选最坏的那个。 三条硬规则：可信边界按依赖判定、终态不自动重开、序号单调闸。

并且不会「两条分支都赢了」：终态独占权单独一道闸，放闸靠凭证而非内容比对。

上下文是有限预算

budget 管输入侧分段计量（区分「工具面膨胀」与「历史膨胀」）， offload 管大对象外置（两阶段：首次只标记）， spill 管输出侧截断与分页取回。

失败是数据表

toolfail 把「类别 → 可重试性 / 退避 / 需人工 / 重发安全 / 模型指引」 做成数据表而非散落的 if。不可归类一律不可重试。

重发安全与重试价值是两个正交维度：超时值得重试，但服务端可能已执行。

N 轮 ReAct 往返塌缩成 1 轮

ptc 让模型写程序、沙箱执行、只把归并后的小结果带回上下文： 原始数据不过模型面。三重预算（墙钟 / 调用数 / 字节数）替代 OS 沙盘， 纯 Go 零 CGO。

派生状态只有一个真相

任何「代次 / 版本 / 序号」只允许有一个真相。需要额外视图时，让它是真相的投影， 不要另开一个计数器——两个计数器在并发下必然漂移。

边界不是文档，是门禁

「内核不许长出领域知识」写在散文里就会烂掉。这里它是机器判据， 全部挂在 make check 上，CI 只执行这一条。

条规则

5 条 go/ast 结构规则

  • harness-facade-stays-facade 门包不许长出实现
  • harness-module-dependency-direction 包间依赖方向
  • 沙箱档位登记（档位声明要有人签字）
  • 执行路径不得绕过沙箱登记簿
  • 子进程出口登记

结构性判定走语法树，不走逐行正则——import 声明有六种以上书写形态。 结构规则清单以 architecture-policy.yaml 的 facades / dependency_direction / sandbox_providers / execution_paths 各段为准。

提交前门禁全链

  • fmt · vet · lint · test
  • cover-gate（全局 60% + 逐包下限 70%）
  • govulncheck（依赖与标准库漏洞）
  • -race（竞态检测）
  • crossbuild（四平台交叉构建）
  • architecture-check（域词 + 依赖方向）
  • docsync（README ↔ 仓库事实一致）

门禁本体全在 make check 里，CI 只执行它——门禁不挂在工作流上变回「推送后门禁」。

门禁的失败形态必须是变红，不是变绿。

改任何判定逻辑，必须同时给「坏实现会红」的用例——只测「好实现能过」的用例， 一个把数字比较写成字符串比较的错实现照样全过。

多工具聚合场景

安装
go get github.com/yi-nology/agent-harness@latest
接一个判定环
import "github.com/yi-nology/agent-harness/dispatch"

// 派发守卫：宿主提供拓扑，harness 提供机制
type myEdgeSource struct{ reg *myRegistry }

func (s myEdgeSource) Slugs() []string                   { return s.reg.Slugs() }
func (s myEdgeSource) DispatchAllow(slug string) []string { return s.reg.Allow(slug) }

g := dispatch.NewGuard(myEdgeSource{reg: reg}, maxDepth)
if err := g.Assert(caller, callee, depth); err != nil {
    // 结构化 *dispatch.DenyError
}
