## 一、结论先行

**差距不在单个能力，在两个维度。**

本仓的**机制面已经很厚**（27 个包，跨进程幂等、租约、栅栏、档位、上下文计量、
失败分类、契约套件……），比多数主流 harness 的「某一项」都深。

真正的差距是：

| 维度 | 主流 | 本仓 | 该不该补 |
|---|---|---|---|
| **A. 装配的运行时性** | DSH：能力可从**配置层**替换（插件树） | 守卫集合**构造后只读** | ⚠️ 归上游/宿主，本仓不该造插件系统 |
| **B. 声明的可撤销性** | DSH：插件可**声明权限、限定边界、记录轨迹、随时撤销** | ①③有、**②④缺** | ✅ **B 是本仓该补的** |
| **C. 平台完整度** | Coze：工作流 UI / 知识库 / 多租户 | 无（内核定位） | ❌ 宿主的事 |
| **D. 端到端执行体** | 各家都有完整 Agent Loop | 只有机制面 | ❌ 宿主的事 |

**一句话**：本仓的差距集中在 **B（声明的可撤销性）**，
而 A 与 C/D 都是**定位决定的**、不该在本仓补。

## 三、本轮核实出的**具体缺口**（本仓该补的）

### 缺口 1：守卫集合构造后不可增删

**实测**：`guardset/guardset.go` 的 `New` 注释明写「构造成功后内部顺序按
(Rank, 装配序) 固定下来，此后 Set 只读，可并发共享」。

**为什么是缺口**：DSH 的「随时撤销」是它安全模型的下半句——
「一切插件都应被声明权限、限定边界、记录轨迹并能**随时撤销**」。
本仓的守卫一旦装配就摘不下来：运行期想临时停掉某个守卫（降级、应急、
灰度），只能**整个进程重启**。

**但要小心**：这**不能**做成「可变的守卫集合」——
`Set` 的只读性是它的**不变量**（并发共享下可变 = 竞态源）。
本仓的纪律是「判据要有一个真相」，可变集合会引入第二个真相。

⇒ **正确的方向不是「让 Set 可变」，而是让「撤销」这件事有明确归属**：
撤销是**装配面**的动作（重建一个 Set），不是**执行面**的动作。
这与本仓既有纪律一致（`netguard` 的「扩展名单整份原子交换」——
换名单是**换整份**，不是改其中一条）。

### 缺口 2：审批与沙箱的**联合判据**没有单点

**实测**：Codex 的两层模型是「沙箱强制 + 审批策略，**两层都同意才放行**」。
本仓这两层分别落在 `sandbox`（档位）与 `policy`（审计门），
**由宿主自己接线**——于是「两层是否都同意」这个判定**没有单点**。

**风险形态**：宿主接了 `sandbox` 但没接 `policy`（或反之），
于是「要求了 OS 级隔离」这个声明**没有任何机制强制它真的发生**。
这正是设计档 §九 第 1 条记的「判不了实际强度是否兑现声明」，
而 §P3-候选 指出它**跨到宿主仓**。

**本仓能做的**：提供一个**联合判据的机制面**——
让「档位要求 + 审批要求」成为**一个可判定的对象**，
而不是两个各自为政的参数。判据归内核，接线归宿主。

**上游覆盖到哪一步（2026-10-21 核实）**：

| 层 | 上游现状 | 缺口 |
|---|---|---|
| 档位 × 预算 | `guardx/sandbox` 的 `Registry.Resolve(min Level, budget...)`——**已覆盖**（选不到满足者即拒绝，绝不降级） | ✅ 无 |
| 审批 | `toolgate/policy` 的 `Mode`/`Verdict`/`Arbiter`/`Rule`——**已覆盖** | ✅ 无 |
| **审批 × 档位（两层是否都同意）** | **两个模块互不知情**（`toolgate/policy` 不 import `guardx/sandbox`，反之亦然） | ❌ **缺口在这** |

⇒ 本仓该补的**不是**「再加一层审批」或「再加一层档位」（那是上游的事），
而是**把两层合成一个判定**——因为「两层都同意才放行」这条规则若由各宿主各接一遍，
必然漂移（这与本仓反复强调的「判定口径必须跨宿主一致」是同一条纪律）。

**落点**：与 `sandbox` 门面同层（核心大概率在上游 `guardx`）。

### 缺口 3：`sandbox` 档位与 `ptc` 实际执行的**一致性**无判据

**实测**：设计档 §P3-候选 已判定这是「真实存在的缺口」，且
「宿主绕过 `sandbox.Registry` 直接调 `ptc.Run`（进程内形态），
于是要求了 OS 级隔离却跑在进程内解释器上——门禁全绿，而实际强度与声明不符」。

**这与缺口 2 是同一件事的两面**：声明面（档位）与执行面（实际走了哪条路）
的一致性，**本仓的门禁只能管本仓自己的代码**。

## 四、明确**不该**在本仓补的（及理由）

| 主流的做法 | 为何不补 |
|---|---|
| DSH 的插件树 / Cordis 组合 | **上游 `oagentkit` 的事**。本仓造第二套 = 与上游并存，正是 `docs/OAGENTKIT-OVERLAP.md` 明令禁止的形态 |
| Coze 的可视化工作流 / 知识库 / 多租户 | 资产（UI + 数据 + 权限模型），内核不该认识 |
| 完整 Agent Loop | 宿主的事（`contract` 就是那条边界） |
| OS 级沙箱（Seatbelt/bwrap/microVM） | 宿主/上游的事。本仓 `ptc` **如实自报 `LevelProcess`**，不谎报更高档——这正是正确的位置 |
| 事件持久化 / 可视化调试 | 宿主的事（`eventbus` 已明确判定「持久化在发布点由宿主负责」） |

## 五、建议的下一轮（按「值不值得做」排序）

### P0：审批 × 沙箱的**联合判据**（缺口 2 + 缺口 3 的一半）—— ✅ **本轮已落地**

**已新增 `gatecheck` 包**：把「审批裁决 + 档位/预算判据」合成**一条**判定。

**它做什么**：只做**合成**，不重新实现任何一层——
审批用上游 `toolgate/policy` 的 `Gate.Decide`，档位用上游 `guardx/sandbox` 的
`Registry.Resolve`。这与本仓「判定归各自机制，组合逻辑归内核」一致
（与 `guardset` / `retryplan` 同族）。

**判据顺序（有意的）**：

| 审批层 | 沙箱层 | 结论 |
|---|---|---|
| 放行 | 选得到后端 | **放行** |
| 放行 | 选不到 | **拒绝**（档位不足） |
| 需人审 | 任意 | **需人审**（优先于档位不足） |
| 拒绝 | 任意 | **拒绝**（优先于一切） |
| 计划模式 | 任意 | **只审不执行**（≠ 拒绝） |

**「需人审」为何优先于「档位不足」**：两条拒绝对宿主处置完全不同——
档位不足该「换环境」，需人审该「去问人」。若先报档位不足，
宿主会去找后端而不是找人，于是这次调用**既没执行也没人管，静默丢失**。

**fail-closed 的两处**：没装审批门 ⇒ 按需人审；要求了档位却没有登记簿 ⇒ 拒绝。

**反向验证**：四条变异（deny 优先级反转 / 需人审优先级反转 /
无登记簿也放行 / 没装审批门也放行）全部打中并变红。

> 变异过程里踩到一个坑：**第一次的「deny 优先级反转」变异根本没反转成功**
> （deny 分支仍插在沙箱层之前），于是用例绿着——看着像「用例没牙齿」，
> 实际是**变异自己没改到点子上**。
> ⇒ 变异不生效时，先怀疑**变异**，再怀疑用例。

#### 补完：从「有个包」到「接进执行链」

第一版的 `gatecheck` 有个**自伤式的问题**：它判完把后端放进 `Decision.Provider`
却不执行——调用方拿那个 provider 自己去 `Exec`，中间任何一步走错就产生
「**判过的后端 ≠ 实际跑的后端**」的落差。那正是本包要消灭的东西。

⇒ 补了两件：
1. **`ExecuteAndRun`**：判定通过就**就地执行**（用判出来的那一个 provider），
   调用方没有「换一个后端跑」的机会；
2. **`Managed`**：**受管后端**——把真后端包起来，判据在 `Exec` 内部、紧挨着执行，
   **不可绕过**。宿主把 `Managed` 注册进登记簿即可。

**门禁的意外收获**：新增 `Managed`（它实现了 `sandbox.Provider`）当场触发
`harness-sandbox-provider-declared`——**档位声明要有人签字**这条纪律在起作用：
新后端必须去 policy 登记。登记时逼出一个真问题：
`Level()` 若返回 `return ManagedLevel`（标识符），门禁静态读到的是
"ManagedLevel"，与登记的 "LevelProcess" 对不上 ⇒ 报「档位漂移」。
⇒ 门禁要能静态比对，代码就必须写成**可静态比对的样子**（`return sandbox.LevelProcess`）。

### P1：撤销的**归属**明确化（缺口 1）—— ✅ **本轮已落地**

**不做什么**：**不**把 `guardset.Set` 改成可变的。
`Set` 的只读性是它的**不变量**（并发共享下可变 = 竞态源），
且本仓纪律是「判据要有一个真相」。

**做了什么**：新增 `guardset.Assembly`——守卫集合的**装配面**，
持有「当前这一份」，并提供**整份换掉**的能力。

| 能力 | 落点 | 为什么是这个形态 |
|---|---|---|
| 撤销 = **换整份** | `Assembly.Swap(ctx, next)` | 改其中一条会让「当前有哪些守卫」出现两个真相 |
| 撤销一条的机械化 | `Set.Without(names...)` | **纯函数**：产出新集合，原集合不变 |
| 原子 | `atomic.Pointer` 换指针 | 在途判定跑在旧份上，下一次跑在新份上；旧份**不被修改** |
| 换份即生效 | `Assembly.Stage()` | 链上那一环指向**装配面**而非某一份 ⇒ 不用重接链 |
| 「谁能换」 | `WithSwapGate` | 授权是宿主的业务决定；本包只给**可判定的接入点** |
| 「换过什么」 | `WithSwapRecorder` + `SwapRecord` | 撤销没有留痕 = 撤销发生过但没人知道 |

**两条边界一起守住**：

- **「全部撤销」不是降级，是失守**——换上去的那份永远非空。空集合在 `New` 就被拒绝，
  `Without` 去掉最后一条返回 `ErrEmptySet`。降级可以撤一条，不能撤到一条不剩。
- **撤销不存在的守卫要报错**（`ErrUnknownGuard`），不静默忽略——
  静默忽略会让宿主以为「撤掉了某条守卫」，实际那份集合里根本没有它。

**反向验证**：7 条单变异 + 1 条**组合**变异全部打红。其中组合变异值得单记：
「换份原地覆盖旧份」与「求值时重读集合内容」**各自单独都不撕裂**
（Go 的 `for _, g := range s.guards` 在循环开始就固定了切片头，
所以原地改旧份也影响不到在途判定），**两者同时出现才真的撕裂**。
⇒ 有些不变式无法用单条变异表达，必须成对组合才能证伪。


### P2：`Store` 参考实现（宿主侧，本仓不做）—— 仍不做

见 [HARNESS-BENCHMARK-20261021.md](HARNESS-BENCHMARK-20261021.md) §七 第 2 条的修订：
**只给契约与套件，不给参考实现**（参考实现会被当生产存储用，
而它恰恰不具备跨进程那条性质）。

### 缺口 3 的另一半：**执行路径与声明面的一致性**（跨仓，仍待拍板）

`gatecheck` 解决的是「声明了要求 ⇒ 判定这次执行能不能满足」，
但**不解决**「宿主绕过 `sandbox.Registry` 直接调 `ptc.Run`」——
那需要**门禁**（宿主仓的 policy），不是运行时判据。

按本仓纪律（`archcheck` 是**可导入的判据执行体**，宿主可复用同一份），
可行的做法是：把「执行路径必须满足声明」做成 `archcheck` 里的一条**可复用判据**，
由宿主仓在自己的 policy 里启用。

**这一条需要与宿主仓对齐后再动**——跨仓改判据落点属于需要拍板的设计决定，
不擅自开工。
