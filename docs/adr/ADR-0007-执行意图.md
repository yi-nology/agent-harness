# ADR-0007 · 执行意图：把「已经打算做」也持久化

| 项 | 内容 |
|---|---|
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-11-11 |
| **背景** | `sideeffect` 的三个判据（幂等键 / 资源租约 / 栅栏令牌）都是**结果**判据——它们回答「做过没有」「谁占着」。但最贵的那个窗口里**结果还不存在**：进程在抢到闸之后、施加成功之后、记账之前直接死掉。此时存储侧既没有「完成」也没有「未知」，只有一把还在的（或刚过期的）闸。下一次同一 Key 的 `Acquire` 把它当成「没做过」⇒ 重新授予执行权 ⇒ **同一动作被施加两次**，而调用方全程只拿到一个普通错误。 |
| **决策** | `Acquire` 在授予执行权时**顺手**把「本次执行的意图」（Key 级 IN_FLIGHT）原子地持久化：它不是结果，是**意图**——只回答「这个 Key 上有一次尝试尚未裁决」。于是：尝试正常收场（完成 / 放弃 / 标记未知）⇒ 意图被裁决掉，Key 回到可执行；进程死在收场之前 ⇒ 意图留在存储里，租约过期后同一 Key 的 `Acquire` **不再授予执行权**，而是转入「需对账态」。配套把两条出口**拆开**：`Abandon`（确定没生效 ⇒ 撤销意图 + 放闸）与 `Release`（**只**放闸，不动意图）。 |
| **后果** | `sideeffect.Store` 接口**新增一个方法**（`Abandon`），**`Release` 的语义收窄**（不再撤销意图），`Acquire` 的判定顺序多一档（执行中 → 需对账态）。共享契约套件 `sidetest` 从 15 条扩到 **22 条**（新增「执行意图」一族六条 + 「闸已释放后续期被拒」一条），并配**负对照**（摘掉意图判据的实现必红）。代价：租约过期且未裁决时，重试需要一次对账——这是「不重复施加」的价格，不是新的失真。 |
| **依据** | `sideeffect/store.go`（契约）、`sidetest/intent.go`（判据）、`sideeffect/intent_test.go`（反向验证）；评审第二轮 P0「At-most-once 缺口」。 |

> **一句话结论**：意图的存在本身就是一条判据——没结论不是「没做过」，
> 而是一次**尚未裁决**的尝试；把它持久化，重复施加的那扇窗才关得上。

---

## 缺口在哪儿

上一版（v0.32.0）给副作用闸加了一等状态「结果未知」：`MarkUncertain` 把 Key
转入未知态，`ResolveUncertain` 由宿主对账后裁决。它封的是**已知的**失败路径——
施加失败且无法判定远端是否已生效。

但它有一个前提：**存储侧得先知道「结果未知」这件事**。而恰恰有两条路径
让存储侧什么都不知道：

1. **标记本身失败**：`MarkUncertain` 写不进去（存储故障）。此时存储侧既没有
   「完成」也没有「未知」——一把闸还开着，下一次 `Acquire` 重新授予执行权。
2. **进程死在标记之前**：施加成功、记账之前进程没了。没有 `Complete`、
   没有 `MarkUncertain`、没有 `Release`——存储侧**一片空白**，
   而下一次 `Acquire` 会把「没做过」当成事实。

两条的共同形态：**「不知道」这件事本身没有被记下来**。

## 为什么不是「在 Runner 里多试几次」

直觉修法是在编排层补偿：标记失败就重试标记、进程死了就让上层重试整个动作。
前者对存储故障无效（故障期间什么都写不进去），后者更糟——**重试整个动作
正是重复施加本身**。

更根本的是：这道洞**在 Runner 层封不住**。进程死亡不是一次函数返回，
编排层根本没有机会执行任何补偿。判据必须落在**存储侧**，而且必须落在
「授予执行权」的那一刻——那是一切尝试的**唯一公共起点**。

## 意图是什么

意图不是结果，也不是「正在做」的同义词。它只回答一件事：

> 这个 Key 上，有一次尝试**尚未裁决**。

于是 Key 级状态多了一档：

```
未开始 ──Acquire──> 执行中 ──Complete──> 已完成
                    │
                    ├──Abandon──────> 已放弃（= 未开始，可重新执行）
                    ├──MarkUncertain> 结果未知 ──ResolveUncertain(true)──> 已完成
                    │                       └─ResolveUncertain(false)─> 已放弃
                    └──租约过期且未裁决 ──Acquire──> 结果未知
```

最后一行是核心：**意图的租约过期了，不等于「没做过」**，只等于「不知道」。
而内核看不见远端，能承认的只有「不知道」——于是转入需对账态，
而不是重新授予执行权。

## 两条出口为什么要拆开

「确定没生效」与「可能已生效」都需要把资源闸放掉，让别的动作能用这个资源。
但它们对**意图**的处理完全相反：

| 场景 | 意图 | 资源闸 |
|---|---|---|
| 确定没生效（准备失败 / 下游会去重） | **撤销** ⇒ 该 Key 重新可执行 | 放 |
| 可能已生效（施加失败 / 记账失败） | **转未知态** ⇒ 该 Key 继续被挡 | 放 |

若只有一条「放弃」出口，且它顺手把意图也撤了，那么「可能已生效」那条路
就会把意图清掉 ⇒ 该 Key 重新变成「可被执行」⇒ **重复施加的入口重新打开**，
且失效是**静默**的——调用方看到的只是一次普通的失败。

所以 `Store` 有了两个名字相近、职责正交的方法：`Abandon`（动 Key 级：
撤销意图 + 顺带放闸）与 `Release`（动资源级：只放闸，不动意图）。
编排层的四条失败出口各自对应一条，不再共用一条「释放闸了事」。

## 与「结果未知」的关系

两者是**同一条红线的两半**：

- 「结果未知」是**有记录**的不知道：有人标了，但还没裁决 ⇒ 需对账；
- 「执行意图」是**无记录**的不知道：没人标（标不上或没来得及标）⇒
  同样需对账。

v0.32.0 只有前半；v0.33.0 补上后半，于是「不知道」有了**两个来源**、
**一条出口**（对账）。

## 边界

本包**不区分**「施加前崩溃」与「施加后崩溃」——两者都可能留下「已施加但未记账」
的世界，故一律转入需对账态。内核要区分它需要下游参与（那正是对账做的事）。
内核能做的只是**如实说「不知道」**，而不是乐观地猜「没做」。

「意图」这个机制面本身也有边界：它是**存储侧**的判据，进程内任何加锁都
替代不了它（与「判据归存储，不归进程」同源）。
