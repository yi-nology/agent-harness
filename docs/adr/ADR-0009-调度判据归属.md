# ADR-0008 · 调度判据的归属：上游没有的那一半落本仓，可达性仍归门面

| 项 | 内容 |
|---|---|
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-11-13 |
| **背景** | issue #108 要求先核对上游 `oagentkit/agent/dispatch` 是否已具备优先级 / 公平调度 / 资源配额 / 背压——**若上游已有，本仓应当是门面而不是另写一份**（AGENTS.md 警告的「与上游并存的第二份实现」）；只有上游确实不提供的部分才在本仓落机制面。 |
| **决策** | 优先级 / 加权公平 / 资源配额 / 背压**四样判据落本仓新包 `scheduling`**（纯函数面，不做队列不做执行）；可达性 / 深度上限 / 自派发的判定**仍归 `dispatch` 门面**，语义跟随上游。两组语义正交：dispatch 回答「能不能派」，scheduling 回答「按什么次序、谁多谁少、满了怎么办」。 |
| **后果** | `scheduling` 以 Experimental 落地（v0.35.0）；宿主把两组语义**串起来**用（先过 dispatch 可达性，再进 scheduling 的排序与配额）。哪天上游收编了四样中的某样，对应判据应当**转门面**而不是并存第二份——这条后续动作写在这里，靠 review 时对 ADR 索引负责。 |
| **依据** | 下文「证据」节（上游 v0.14.10 的完整判定面清单 + 逐文件核对）；`architecture-policy.yaml` 的 `modules` 段（scheduling 登记）；`docs/OAGENTKIT-OVERLAP.md`（与上游的分工文档）。 |

> **一句话结论**：调度判据的归属靠证据不靠感觉——上游 `dispatch` 的全部判定面
> 是 allow 矩阵 + 深度 + 自派发三条，优先级 / 公平 / 配额 / 背压上游确实没有，
> 于是判据面落本仓 `scheduling`，可达性仍归门面；本仓不出现与上游语义重复的实现。

---

## 证据（issue #108 验收第一条：结论写证据，不写「感觉」）

上游模块 `github.com/oagentkit/agent@v0.14.10` 的 `dispatch` 包
（`dispatch/dispatch.go`，全文核对）导出符号全集：

| 符号 | 判定内容 |
|---|---|
| `Guard.Assert(caller, callee, depth)` | 三条分支：自派发（caller==callee）→ 深度超限（depth ≥ maxDepth）→ allow 矩阵不可达 |
| `Guard.AssertDepth(depth)` | 仅深度（环节推进用） |
| `Guard.Allowed(caller, callee)` | 只读查询可达性 |
| `DenyError` / 三个 `Reason` 常量 | `not_allowed` / `depth_exceeded` / `self_dispatch` |
| `NewGuard` / `EdgeSource` | 构建期物化 allow 矩阵 + 环检测 |

**没有**优先级排序、没有公平份额、没有配额账本、没有背压裁决——四样在
上游模块的符号表里不存在（不是「有但不同名」：`Assert` 的三条分支就是
上游 dispatch 的全部运行期判定）。

同批核对的相邻上游面：`oagentkit/toolgate`（审批裁决）、`oagentkit/guardx`
（沙箱档位与失败分类）同样不含调度四样——它们管的是「单次调用准不准」，
不是「一批调用怎么排」。

## 为什么判据面（而不是队列、不是执行器）

与 `guardset` / `retryplan` / `gatecheck` 同一条分工：**组合逻辑归内核，
判定归各自机制；执行归宿主**。调度四样在本仓的形态是纯函数 / 确定性
状态机：

- **优先级**（`Order` / `TopK`）：确定性排序——平局有名字层裁决，
  输入排列顺序不影响结果（否则一次无关的配置重排就换掉执行次序，
  宿主没法解释「为什么它先跑」）；
- **公平份额**（`FairPicker`）：加权欠账选择——按 `served_i/w_i` 最小者
  先服务，平局按名字；确定性可复现；
- **配额**（`Quota`）：账平判据——整单占用（不做部分占用，半截状态
  会多一种回滚写法）、超释放显式拒绝（钳位会把重复释放吞成静默）；
- **背压**（`Policy.Decide`）：拒绝必须带机器可判的原因
  （`queue_full` / `in_flight_full`），且**在途满优先于队列满**——
  容量问题的处置是扩容/收敛，拥塞问题的处置是退避，先报哪条决定
  宿主去找谁（与 `gatecheck`「需人审优先于档位不足」同一思路）。

本包不实现队列本体、goroutine 池、执行循环——那是宿主的活；也不判
可达性——那是 dispatch 门面的活。挑选策略接进领取驱动的钩子（`worker.Config.Pick`）
是宿主的接线，不是本包的执行面。

## 不出现第二份实现的后续动作

上游若在 `dispatch` 收编四样中的某样：本仓把对应判据**转门面**
（类型别名 + 单条转发，进 policy 的 `facades` 段），删除本地实现。
这遵循 ADR-0005（门面包不可变）的同一条纪律——判断依据是上游符号表
（本 ADR 的证据节给出当时的基线 v0.14.10），升级上游时逐条比对即可。
