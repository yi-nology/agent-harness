# 对标五家 Agent Harness：借鉴项与归属判定（2026-10-21）

> 本文回答一个问题：**拿到「Codex / DSH / Octop / Yi-nology / Coze」五家对比后，
> 本仓（agent-harness）该改什么、不该改什么。**
>
> 判定依据是本仓自己的边界纪律（见 [../AGENTS.md](../AGENTS.md)）：
> **机制 → 本仓；资产 → 宿主仓。** 不因「别家有」就往本仓塞。

## 一、对比材料里点名本仓的三处缺口（原文摘录）

对比材料对 Yi-nology（本仓）的判断是：

> 同样，Yi-nology 当前也尚未构成完整的分布式 Exactly-Once 执行系统；
> 它有更明确的约束机制，但仍需要**持久化租约、幂等键和资源侧的并发控制**。

以及能力对比表里的一行：

| 能力维度 | Codex | DSH | Octop | Yi-nology | Coze |
|---|---|---|---|---|---|
| 跨进程执行独占 | 需具体验证 | 需具体验证 | 需具体验证 | **部分机制** | 需另行增强 |
| 工具调用安全 | 较完善 | 支持 | 支持 | 多守卫门禁 | 需加强执行隔离 |

这三条是**对比材料唯一点名本仓**的缺口，且都被归在 P0
（「分布式执行安全与副作用控制」）。本轮据此落地。

## 二、落地前的核实：上游矩阵有没有现成原语

本仓纪律：**机制面若上游已有，就不该在本仓造第二份。**
故动手前先查了 `oagentkit` / `oekit` 全部模块（`agent` / `guardx` / `runtime` /
`toolgate` / `llm` / `oekit/pkg`）：

| 候选 | 结论 |
|---|---|
| `guardx/fence` | **不是栅栏令牌**——是 markdown/HTML 注入卫生（`EscapeUntrusted`），与并发无关 |
| `oekit/pkg/singleflight` | **进程内**去重，不跨进程，且无持久化语义 |
| `oagentkit/agent/agentrun/sideeffect.go` | **进程内观测**（动词表启发式判断「本次是否调用过变更类工具」），只用于「跳过整体重试」，**不做去重** |
| `guardx/permgate` | 能力/权限判定，非租约 |
| 上游有无 `LeaseStore` / `IdempotencyKey` / fencing token | **全仓无**（grep 确认） |

结论：**租约、幂等键、栅栏令牌在第一方矩阵内无对应物**，
本仓补这三样不是造第二份，而是补第一份。

## 三、本轮落地：`sideeffect` 包

新增包 [`sideeffect/`](../sideeffect/)：副作用「至多一次」的跨进程契约。

### 3.1 为什么是三样东西而不是一样

三个失效形态互相独立，缺一不可：

1. **幂等键** —— 同一逻辑动作被重试（超时重发、恢复后重跑、两个 worker 都以为该做）
   → 同一 Key 只施加一次，后到者取回先到者的结果。
2. **租约** —— 两个 worker 同时想做同一资源上的动作 → 同一资源同一时刻至多一个持有者，带 TTL。
3. **栅栏令牌** —— 持有者过期后又回来写入 → 每次接管发一个单调递增的令牌，
   下游凭「令牌比已见过的旧」拒收。

第 3 条是前两条都盖不住的：**租约过期 ≠ 持有者已死**。
持有者可能只是 GC 停顿或网络分区，恢复后仍拿着已过期的租约去写。
若下游只认「谁拿着租约」而不认「拿着的是哪一代」，
那么一份两小时前签发的租约仍能覆盖掉别人这两小时写下的新状态——
**更新的数据被旧数据覆盖**。

### 3.2 三个判据必须共享一个真相

幂等键、租约、栅栏令牌**不是三份独立状态，而是一份状态的三个投影**。
本包的 `Store` 只有**一个** `Acquire` 入口，一次返回三者的联合判定。

若拆成三份存储、三次独立写入，就会出现一个窗口：
租约判定说「你占着」而幂等判定说「没做过」——两者都自洽，
合起来却允许同一动作被施加两次。

这与本仓既有纪律同源：
- 「派生状态只能有一个真相」（令牌是闸的投影，不是第二个计数器）；
- 「判据归存储，不归进程」（`checkpoint/cas.go`）——跨进程的判据必须在存储侧判。

### 3.3 与既有包的分工（不重复造）

| 包 | 管什么 | 与 `sideeffect` 的边界 |
|---|---|---|
| `commitgate` | 环节**终态**只被提交一次 | 管的是「状态写」；`sideeffect` 管的是「对外部世界的动作」。前者进程内、凭令牌放闸；后者跨进程、凭幂等键去重 |
| `checkpoint` | 进度快照的跨进程 CAS | 管的是「恢复点不回退」；`sideeffect` 管的是「动作不重复施加」。快照恢复后重跑的那一步，正是 `sideeffect` 的用武之地 |
| `toolfail` | 工具失败的**分类契约**（含重发安全三态） | 回答「这次失败该不该重试」；`sideeffect` 回答「重试了会不会重复施加」。两者是**互补**，不是重叠 |

## 四、明确**不**进本仓的项（判定与理由）

对比材料的 P1/P2 里多数项属于宿主或平台层，本仓纪律下不能接：

| 对比材料的建议 | 归属 | 理由 |
|---|---|---|
| 可视化 Workflow Builder（Coze / FlowGram） | **宿主仓** | 资产（UI / 编排图），且对比材料自己就警告「不建议为使用可视化 Workflow 而直接 Fork 整个 Coze 项目」 |
| Agent / Tool / Skill 注册表（DSH、Octop） | **上游 `oagentkit`** | 上游已有 `agent` / `toolgate` 等模块；本仓造一份即「与上游并存的第二份实现」 |
| 统一模型路由（Octop、Coze） | **上游 `llm`** | 上游已有 `llm` 模块（含 failover / retry / stage_router） |
| 长期记忆与知识库（Octop、Coze） | **宿主仓** | 资产（数据 + 检索策略），内核不该知道 |
| 持久化 Session Event Log（DSH） | **宿主仓** | 本仓 `eventbus` 明确是「进程内有损广播；持久化在发布点由宿主负责」——这是既有判定，不在「借鉴」名义下推翻 |
| OS 级沙箱（Codex、DSH） | **上游 `oagentkit` / 宿主** | 本仓 `ptc` 是 **goja 进程内 VM**（三重预算替代 OS 沙盘），定位不同，不改 |
| 多租户 / 业务资源管理 | **宿主仓** | 资产，且需要真实的权限模型 |

**一句话**：本轮只接了「对比材料唯一点名本仓、且上游没有、且属机制面」的那一项。

## 五、本轮**没有**解决的问题（显式记录，避免被当成已完成）

1. **本包不提供 exactly-once**。承诺的是「至多一次」——这是可达的上界。
   exactly-once 要求**下游也接受幂等键**（把 Key 传到下游写入请求里），
   那是宿主的接线责任。把上界说成 exactly-once 是本包明确拒绝的一种失真。
2. **`Store` 的原子性无法在本仓验证**。本包给的是契约（「Acquire 必须是
   一次原子操作」），跨进程正确性由宿主的存储实现保证。
   本仓能测的只是「内核不依赖它是否原子」的编排层语义——
   用例用的是内存替身（`fake_store_test.go`），它自己就实现了那把锁。
3. **下游资源侧的栅栏校验不在本包**。本包负责**发**令牌；
   下游怎么拒收陈旧写入（记住见过的最大令牌）是宿主资源的事。
4. **租约的续期（Renew）未提供**。当前只有获取 / 记账 / 释放三步，
   长耗时动作需要宿主自己在存储侧续期，或调用方另做安排。

## 六、门禁与验收

- 声明先行：先在 `architecture-policy.yaml` 的 `modules` 段登记
  `sideeffect`（`requires: ["ext:github.com/oekit/pkg"]`），
  并把它加进 `thresholds.scan_roots`（漏了则该包对「超长文件」「god object」
  两条阈值**完全隐形**——policy 自校验强制两者一致）。
- 反向验证：五条变异全部打中并变红（栅栏校验、令牌单调性、判据优先级、
  失败记账、失败释放），不是「只测好实现能过」。
- `make check` 全绿（含 `docsync` 包表一致性）。

## 六之二、第二轮：`sidetest` 契约套件（兑现 §七 第 2 条）

§七 第 2 条记的是「`Store` 的参考实现 / 可复用契约测试套件」。
本轮补上**契约测试套件**（`sidetest` 包），参考实现那一半**故意没做**
（见 §七 修订）。

### 为什么需要它

`sideeffect.Store` 的正确性无法靠「看起来对」保证：它要跨进程、靠一次原子
操作维持三个判据的联合，而**每一家宿主都会自己写一遍存储实现**。
各写一遍必然各判一套，语义漂移开到没人发现为止。

`sidetest` 把「宿主实现必须满足什么」固化成**一组可复跑的子测试**：
宿主写完存储实现后把套件接进自己的测试跑一遍，违反哪条契约就红在哪一条。

### 范式沿用上游，硬失败不静默跳过

沿用 `oekit/pkg/cache/cachetest` 与 `pkg/singleflighttest`（同家族的做法）：

- **8 条子测试**对应 8 个真实失效形态：只做一次 / 已完成优先于占用 /
  未过期时争用 / 过期后接管 / 令牌单调 / 过期持有者不得记账 /
  过期持有者不得放闸 / 释放不等于完成。
- **入口一律 `t.Fatalf`，不 `t.Skip`**：显式接入套件＝声明「我这个实现要满足
  副作用闸的契约」，此时跳过一个场景等于把「我没测过」伪装成「我通过了」。
- **时钟可注入**（`ClockedStore` 接口）：过期场景若读真实时间就恒不触发，
  套件会退化成一组空断言。

### 套件自身也做了反向验证

套件若没有牙齿，它给宿主的「验收标准」就是假的。
本轮用五条变异实现验证套件能抓出坏实现，每条都精确命中对应子测试：

| 变异实现 | 被哪条子测试抓住 |
|---|---|
| 不认识幂等键（已完成当成没做过） | `apply_once` + `completed_wins` |
| 令牌不单调 | `takeover_after_expiry` + `fence_monotonic` + `stale_complete_rejected` + `stale_release_rejected` |
| `Complete` 不校验栅栏令牌 | `stale_complete_rejected` |
| `Release` 不校验栅栏令牌 | `stale_release_rejected` |
| 租约永不过期 | `contended_while_held` + `stale_release_rejected` |

### 顺带补上的契约漏洞

写套件时发现 `sideeffect` 的 `Store.Acquire` **没有 TTL 参数**——
租约时长根本没进契约，宿主只能自己硬编码（要么太长、别人迟迟拿不到闸；
要么太短、自己的动作还没做完就被接管）。已修为 `Acquire(ctx, act, ttl)`，
并把「TTL ≤ 0」显式判为非法（零值不表示「无限期」，那会让一道闸永远关着）。

这是「先写契约测试套件」的一个额外收益：**套件逼出了契约本身的漏洞**。

## 六之三、第三轮：仍未解决

- **参考实现仍未提供**（`sidetest` 只给套件，不给实现）。理由见 §七 修订。
- **租约续期（Renew）仍未提供**——需要先定「续期失败怎么办」的语义。
- **下游资源侧的栅栏校验不在本包**：本包负责**发**令牌，下游怎么拒收
  陈旧写入是宿主资源的事。

## 七、下一轮可考虑的方向（按优先级）

1. **租约续期（Renew）**：`sideeffect` 当前没有续期接口，长耗时动作的租约
   只能等 TTL 自然过期。补它需要先定「续期失败时怎么办」（放弃本次动作？
   还是续到成功？）——这是**语义选择**，不应急着写。
2. **~~`Store` 的参考实现~~** → 改为：**只给契约测试套件，不给参考实现**
   （`sidetest` 已于第二轮落地，见 §六之二）。

   为什么**不**给参考实现：一份「正确的内存实现」会被宿主当成生产可用的
   存储——而它**恰恰不具备本包最核心的那条性质**（跨进程）。
   单进程内存实现无法提供「Acquire 是跨进程原子操作」，
   拿它上生产 = 以为自己去重了，实际两个进程各做一次。
   套件则不同：它**只判语义、不提供实现**，用错了最多是「测了但没测到跨进程」，
   不会伪装成「有去重保障」。

   宿主真需要参考实现时，正确做法是看 `sidetest` 里的
   `sidetest_test.go`——那份按契约写的最小实现是**测试夹具**，
   不是可交付的存储。
3. **与 `toolfail` 的接线**：`toolfail` 判「该不该重试」，`sideeffect` 保证
   「重试不重复施加」——两者配套能让重试策略从「拍脑袋」变成「有兜底」。
   （注意：`toolfail` 正被迁往上游 `guardx/toolfail`，接线时要按迁移后的路径走。）
