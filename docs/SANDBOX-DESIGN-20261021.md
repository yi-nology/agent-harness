# 执行沙箱的下一层：跨域执行与资源兜底（设计档，2026-10-21）

> 一句话：**「执行沙箱」接下来做什么、不做什么。**
>
> 范围声明：本档是 **agent-harness 侧对上游 `guardx` 的需求与分工**。
> 机制（档位语义、跨进程协议、预算面）落在 `oagentkit/guardx` 仓；
> 本仓只保留**门面**与**执行后端**（与 `sandbox` / `toolfail` 本次下沉的分工同构，
> 见 [OAGENTKIT-OVERLAP.md](OAGENTKIT-OVERLAP.md)）。
>
> 本档所有「现状」一节都带出处，且在 2026-10-21 实测过——**不靠记忆**。

## 一、现状核实

| 事实 | 出处 |
|---|---|
| 档位语义（`Level` / `Provider` / `Registry` / `Execute`）已在 `guardx/sandbox` v0.9.0 | `go.mod` `github.com/oagentkit/guardx v0.9.0` |
| 本仓 `sandbox` 是**门面**（类型别名 + 常量别名 + 转发函数） | `sandbox/sandbox.go` 包头；`policy.yaml` 的 `facades` 段已登记 |
| 核心语义：**选不到满足档位的后端即拒绝，绝不降级**；取**最弱**满足者 | `guardx/sandbox` 包头 |
| 唯一的执行后端是 `ptc`（goja 进程内解释器，`LevelProcess`） | `ptc/provider.go` |

## 二、这一轮挖出来的真缺陷：内存无兜底，而包头说它有

`ptc` 的包头写着：

> 恒返回 Result 不 panic——失控循环/**内存风险**由三闸治理（spec §5）。

**这句话是假的。** 三闸是墙钟（`DefaultTimeout`）、绑定调用数（`DefaultMaxCalls`）、
输出字节数（`DefaultMaxBytes`）——**没有内存这一闸**。而 goja 的公开 API 里
**没有任何内存限制**（只有 `SetMaxCallStackSize`，那是调用栈深度）。

后果不是理论上的：一个模型写的 JS 只要 `while(1) arr.push(new Array(1e6))`，
就能在 30 秒 deadline 到点**之前**把宿主进程的内存吃光，宿主被 OOM 杀掉——
而宿主进程里还跑着编排引擎、事件总线、别的环节。

这不是「未来 OS 级后端的远期需求」，是**今天就在的可用性缺陷**：
一个不可信程序能杀掉宿主。

**它同时也是路径依赖**：要兜住内存，只能把执行搬出宿主进程
（Go 运行时没有「只给一个 VM 限内存」的开关；`debug.SetMemoryLimit` 管的是整个进程）。

## 三、为什么先做「执行出宿主进程」，而不是先做 OS/VM 级后端

| 候选 | 判断 |
|---|---|
| **OS/VM 级后端**（容器 / microVM） | **现在不做**。① 地基未建：程序在隔离域里要回调宿主工具，必须有一条跨进程通道，而它不存在——先做后端等于在没有地基的地方盖二层楼；② 本地没有可用的 OS 级底座（seatbelt 废、microVM 无），容器后端要给内核引入 docker 运行时依赖；③ 价值前提未被证明：需要它的是「解释器会逃逸」（CVE 级假设）与「更强的能力裁剪」，而今天更强的能力裁剪在 `ptc` 的 JS 子集 + 绑定白名单下已经拿到了 |
| **执行出宿主进程**（子进程 + 跨进程通道） | **现在做**。① 它同时修掉第二节那个真缺陷；② 它是任何未来 OS/VM 级后端的**必需件**（通道）；③ 本地就能做（子进程 + `rlimit` + 管道），不引外部运行时依赖 |

一句话：**先铺地基，再盖楼**。地基这一层同时有独立收益（内存兜底），
所以它不是「为未来铺路」的纯投入。

## 四、落位：通道归上游，运行时归后端

这是本设计最要紧的一刀。**跨进程通道是机制，程序运行时是后端的事。**

| 层 | 归属 | 交付什么 |
|---|---|---|
| 协议与骨架 | **上游 `guardx/sandbox`**（新增 `wire`） | 帧格式、类型化失败、`Transport`、父侧服务端循环（执行绑定 / 记账 / 限流）、子侧客户端 |
| 执行后端 | **本仓 `ptc`** | goja 子进程后端：子进程里跑 goja，绑定换成走管道的 `Binding`；用 `rlimit` 兑现内存上限 |
| 档位与预算要求 | **上游 `guardx/sandbox`**（扩展 `Budget`） | 宿主要求「这次执行要多少隔离 + 多少兜底」 |
| 选哪个后端 / 起子进程 | **宿主** | 登记后端、声明档位、决定「怎么起这个进程」 |

**为什么这么切**：协议要传的是「调用一个工具」的通用约定，与「程序用什么语言写」
无关；而 goja 是 `ptc` 的实现细节。内核不该知道程序长什么样——
这与 `sandbox.Request.Program` 的既有约定一致（注释原文：「后端自己解释 Program」）。

**「怎么起子进程」是部署面的事，协议不规定**：re-exec 宿主自己的二进制、
还是跑一个镜像，由后端/宿主决定。协议只管「起来了之后怎么说话」。

## 五、协议：`sandbox/wire`（在上游落地）

### 帧格式

长度前缀 + JSON（**不是**行分隔——工具输出可能含换行，行分隔会被内容切断）：

```
┌───────────────┬──────────────────────────────┐
│ 4B 大端长度 N  │ N 字节 JSON 负载             │
└───────────────┴──────────────────────────────┘
```

请求帧：

```json
{"v":1,"id":"c-3","tool":"get_logs","args":"{\"host\":\"h1\"}","deadline_ms":5000}
```

响应帧：

```json
{"v":1,"id":"c-3","ok":true,"value":"OUT<...>"}
{"v":1,"id":"c-3","ok":false,"kind":"permission_denied","error":"..."}
```

### 六条不变量

1. **版本响亮失败**：`v` 不匹配即拒，不静默错配（错配的症状是「字段读成了另一个意思」，
   那是最难查的一类）。
2. **失败分类跨进程同源**：`kind` 取 `guardx/toolfail` 的分类
   （`transient` / `permanent` / `authentication` / `not_found` / `permission_denied` /
   `invalid_argument` / `rate_limited` / `self_reported` / `unknown`），
   **不是**自由字符串。分类一旦退化成字符串，宿主就分不清「可重试」与「永久拒绝」，
   重试策略随之瞎掉。`toolfail` 与 `sandbox` 同在 guardx，**同层引用，无跨仓依赖**。
3. **预算的权威在父侧**：调用数与输出字节数由**宿主侧**记账。子进程只是执行者——
   若子进程自己记账，它可以谎报自己没超预算。
4. **在途调用有硬上限**：总量预算（`MaxCalls`）拦不住「瞬间发起十万次并发调用」——
   那时它们都还没返回，父侧已被 goroutine 淹没。故父侧另设**在途并发上限**，
   超出即回「超限」。这是**可用性**约束，与 `MaxCalls` 的**配额**约束是两件事。
5. **取消传播**：父侧 ctx 取消 → 取消在途调用 + 通知子进程终止（否则子进程继续跑，
   父侧却已经返回了）。
6. **响应按 `id` 关联，不按到达顺序**：程序里多个 `await` 是并发的，
   返回顺序与请求顺序无关。

## 六、档位模型：不新增一维，兜底需求走 `Budget`

### 为什么不是给 `Level` 加一维

我一度想加一维「资源兜底（Containment）」，理由是「子进程 + `rlimit`」这个后端
在现有 `Level` 阶梯上无处安放：它的能力面是解释器白名单（同 `LevelProcess`），
资源面是内核兜底（更强），文件/网络面未裁剪（比 `LevelOS` 弱）——**一维说不通**。

但改用「兜底是**预算项**」之后，一维阶梯保持成立，且不必动 `Level`：

- `Level` 继续管**能力面**（安全维度），单调可比，语义不变；
- **资源兜底**是**正交**的一维，而它**本来就有一个位置**：`sandbox.Budget`。
  预算的本质就是「这次执行要多少资源」——`WallClock` / `MaxCalls` / `MaxBytes`
  已经是三个要求项，**内存只是漏了第四个**。

于是：

```go
// Budget（上游 guardx/sandbox，提案）
type Budget struct {
    WallClock time.Duration
    MaxCalls  int
    MaxBytes  int
    // MaxMemory 内存上限（字节）。0 = 不要求。
    //
    // 进程内后端**兜不住**这一项：Go 运行时没有「只给一个 VM 限内存」的开关，
    // 而解释器本身也没有内存限制 API。故要求它的宿主会拿到明确拒绝，
    // 而不是「以为兜住了、实际没有」。
    MaxMemory int64
}
```

### 后端的支持面：**可选接口**，不改已发布的 `Provider`

```go
// Capable 可选能力面：后端能否兑现这组预算。
//
// 刻意是**可选接口**而非 `Provider` 的新方法：`Provider` 已在 guardx v0.9.0
// 发布，改它对已实现的宿主就是破坏性变更。可选接口则让既有实现**编译期零改动**，
// 且缺省语义天然是保守的——
//
//	不实现 Capable ⇒ 只兑现基本三闸，**不兑现内存** ⇒
//	要求 MaxMemory 的请求不被选中 ⇒ fail closed。
type Capable interface {
    Supports(b Budget) bool
}
```

**选择规则**：`Resolve` 在满足档位下限的候选里，进一步要求它 `Supports(req.Budget)`；
不满足者**不被选中**（不是选中后失败）。无候选即 `ErrNoProvider`——
与「不降级」同一条纪律：**要求与实际之间不允许有静默落差**。

**顺带修掉一个今天就存在的隐性落差**：`ptc` 现在收到 `MaxBytes` 之外的需求也一律忽略，
而 `Budget` 里根本没有内存项，宿主**无从要求**。加了 `MaxMemory` 之后，
「要内存兜底」成为一句可声明、可判定的话。

## 七、失败形态清单（每条都要可判定）

| 形态 | 谁判定 | 判定方式 |
|---|---|---|
| 档位不足 | 登记簿 | `Resolve` 返回 `ErrNoProvider`（不降级）|
| 兜底不足（要求了内存，后端兜不住）| 登记簿 | `Supports` 为假 ⇒ 不被选中 |
| 子进程起不来 | 后端 | `Exec` 返回错误，**不静默退回进程内执行** |
| 子进程崩了 | 后端 | 管道 EOF ⇒ 报「执行域异常终止」，不是「程序返回空」 |
| 协议版本不符 | 两侧 | 响亮拒绝 |
| 工具失败 | 父侧 | 按 `toolfail` 分类回帧，**分类不失真** |
| 在途调用超限 | 父侧 | 回「超限」帧，**不排队等** |
| 父侧 ctx 取消 | 父侧 + 子侧 | 取消在途调用 + 通知子进程终止 |
| 解释器逃逸（假想）| 宿主 | 子进程边界天然兜住——**这正是执行出宿主进程买到的** |

### P2｜需求驱动：容器 / microVM 后端 —— **本仓不做，宿主自己做**

- 用 P1 的协议，只是把子进程换成容器（`LevelOS`）或 microVM（`LevelMachine`）。
- **前置**：本机要有底座。当前只有容器（Docker Desktop），且要给内核引入 docker 依赖
  ——这一步要不要做，取决于宿主是否真的需要比「解释器白名单」更强的能力裁剪。

#### 2026-10-21 判定：**本仓不参与 P2**（理由与实测）

P1 落地后，**宿主实现容器后端完全不需要本仓参与**——实测（2026-10-21）：

```go
// 宿主自己的代码，只依赖 guardx
type containerBackend struct{}
func (containerBackend) ID() string           { return "my-container" }
func (containerBackend) Level() sandbox.Level { return sandbox.LevelOS }
func (containerBackend) Supports(b sandbox.Budget) bool { return true }
func (containerBackend) Exec(ctx context.Context, req sandbox.Request) (sandbox.Outcome, error) { … }

reg := sandbox.NewRegistry()
_ = reg.Register(containerBackend{})
p, _ := reg.Resolve(sandbox.LevelOS)   // → 选中 my-container
```

`sandbox.Provider` 就是那个扩展点：ID / Level / Supports / Exec 四个方法，
`Registry` 按「档位下限 + 预算可兑现性」挑后端。宿主想上容器就自己实现并注册，
**本仓一行都不用改**。

故 P2 的形态是：**宿主侧工作，不是内核侧工作**。本仓若再写一个容器后端，
就变成「同一个机制两份实现」——正是 `OAGENTKIT-OVERLAP.md` 明令禁止的形态。

**本仓不做 P2 的三个理由**：

1. **价值前提未被证明**（本档 §三 已论证）：今天更强的能力裁剪在 `ptc` 的
   JS 子集 + 绑定白名单下已经拿到了；需要 OS/VM 级的是「解释器会逃逸」
   （CVE 级假设）与「更强的能力裁剪」——前者是假想，后者宿主自己判断。
2. **要给内核引入 docker 运行时依赖**：本仓是编排内核，依赖地板受
   `architecture-policy.yaml` 的 `ext:` 声明约束；为一个**尚未证明需要**的
   后端抬地板不划算。
3. **本地/CI 不可复现**：容器后端要拉镜像，本机有 Docker Desktop，但 CI
   跑不了——门禁要求覆盖率与测试在 CI 上可跑。

**若宿主确实需要**：按上面那段实现 `sandbox.Provider`，注册进 `sandbox.Registry`，
本仓不动。若走 microVM，`Level` 填 `LevelMachine`，`Supports` 按实际兑现的
预算项声明。

### P3｜本档原本没有这一期（2026-10-21 记录）

**本档初稿的分期只有 P0 / P1 / P2。** 收到「做 P3」的指令时核对全文，
确认没有第四期——不是漏写，是**初稿就没规划**。

按 P1/P2 落地后的现状，**唯一还没被覆盖的、且值得做**的一期是「P3-候选」：

#### P3-候选：把「跨域执行」这条纪律**从文档变成门禁**

现状：`sandbox` 的核心语义（选不到满足档位的后端即拒绝、**绝不降级**）由
上游 `guardx` 的 `Registry` 保证；本仓侧的对应保证是**档位登记门禁**
（`harness-sandbox-provider-declared`：登记的档位/支持面必须与代码事实一致，
且每个后端都要有人签字）。

**但还缺一条**：本仓的门禁只核对「登记 ↔ 代码事实」，不核对
「**实际执行用的后端**是不是登记过的那个」。形态是：宿主绕过 `sandbox.Registry`
直接调 `ptc.Run`（进程内形态），于是**要求了 OS 级隔离却跑在进程内解释器上**
——门禁全绿，而实际强度与声明不符。

这正是本档开篇那句判据的下一环：「**档位表是宿主做风险判断的依据，说谎的成本
落在宿主身上**」。而现在说谎的**不是**档位表，是**执行路径**。

**要做的**：
1. 门禁新增一条：`harness-sandbox-execution-path`——当宿主声明了「本次执行要
   哪一档 + 哪些预算项」时，实际走的执行路径必须满足它（走 `sandbox.Registry`
   的登记后端，且该后端的 `Supports` 满足要求）。
2. 判据落点：宿主侧的接线（本仓是内核，判宿主行为需要宿主仓的 policy——
   本仓的门禁只能管本仓自己的代码）。

**难点（写明，不假装简单）**：这条门禁要跨到宿主仓（bianque），而本仓的门禁
只看本仓。可能的做法：
- 由宿主仓自己的 archcheck 实现（同一条判据，两边各有一份实现 —— **违反
  「判据只有一份」**，故不取）；
- 或把判据做成**可导入的判据包**（本仓 `archcheck` 已是这种形态，宿主复用
  同一份执行体）——**这条更可行**，且与本仓「门禁执行体必须可被宿主复用」
  的既有纪律一致。

**结论**：P3-候选是一个**真实存在**的缺口（执行路径与声明面的一致性），但它
**跨仓**，且落点需要与上游/宿主对齐后再动。**不擅自开工**——这属于需要
拍板的设计决定，不是「照着做」的实现任务。

**「上游 `Provider` 无状态化」这件事：当前不需要**（记录取舍，免得下轮重复讨论）——

Bindings/Stages ⇒ 「进程级登记簿」与「按次构造后端」有张力。

| 形态 | 语义 | 代价 |
|---|---|---|
| **A（已采用）** 按次建登记簿：每次执行建一个 Registry、注册一个后端、执行完丢 | 核心语义**仍然成立**——候选只有一个时，「档位不足 ⇒ `ErrNoProvider`」「兜不住预算 ⇒ 不被选中」与候选数无关（`Resolve` 的核心判定只看档位与 `Supports`）| 「选最弱满足者」在多后端场景退化（只有一个候选）|

## 九、已知局限与待决项

1. **判不了「实际强度是否兑现声明」**。`Level` 与 `Supports` 都是后端自报的。
   门禁保证的是「声明可见、不漂移、有签字」，不是「隔离真的到位」。
2. **子进程后端的启动方式未定**。re-exec 宿主自己的二进制（需要宿主在 `main` 里
   判一次环境变量）还是随包发一个小二进制（宿主要安装它）——**影响接入成本**，
   待定。

   **2026-10-21 补：re-exec 的失败形态已查清并已兜住。**
   宿主若**忘了**在 `main` 里调 `ptc.MaybeRunChild()`，子进程会跑起**宿主的完整
   main**——它不退出（正常启动服务）、也不回 Result 帧 ⇒ 父侧**永久挂死**
   （上游 `guardx/wire` 的 `Starter.Start(ctx, ...)` 收了 ctx 却不用它，
   `ReadFrame` 是无超时的阻塞读；`ctx` 取消也救不了）。

   本包已兜住：父侧**自己**给「等结果」加期限（取 `ctx` deadline 与墙钟预算中
   较早者），到期即报错收场并收刀；错误信息**直接指向真因**：

   > wire: 等子进程结果超时——子进程未回报结果且未结束
   > （宿主是否忘了在 main 里调 `ptc.MaybeRunChild()？）

   ⇒ re-exec 的**接入陷阱**从「静默挂死」变成「一条能照着改的错误信息」。
   这也**没有**替宿主做决定（第 2 条本身仍待定：随包发小二进制能彻底消除这个
   陷阱，代价是宿主要多装一个东西）。
3. **管道往返有延迟**（2026-10-21 已实测，见下）。

   实测（macOS 27 arm64，本仓 `ptc` 的 `subprocess_bench_test.go`）：

   | 口径 | 数值 |
   |---|---|
   | 子进程**启动成本**（一次性：起进程 + goja 初始化 + 管道建立） | **≈ 13.4 ms** |
   | 子进程内**每次工具调用的边际成本**（差分法，扣掉启动） | **≈ 174 µs** |
   | 进程内**每次工具调用**（含 goja 解释 + 判定环） | **≈ 4.1 ms** |

   **结论与初稿的猜测不同，值得写明**：

   - 初稿猜「百纳秒到几十微秒」，实测是 **174 µs**——比猜测**慢约一个数量级**。
   - 但**子进程路径在多次调用时反而更快**（50 次调用：子进程 103 ms vs
     进程内 206 ms）——因为 goja 只在子进程里初始化**一次**，
     而进程内路径每次调用都走完整判定环。
   - ⇒ **别按「IPC 一定更慢」做决策**：一次性调用选进程内（省 13ms 启动），
     程序内循环上百次选子进程（省每次 4ms 的解释开销）。

   测法（可复现）：**差分法**——`(T(50) − T(1)) / 49`。直接测「N 次耗时」
   会把启动成本摊进每次调用，严重高估往返成本。

   复现命令：`go test ./ptc/ -run TestSubprocessMarginalCallCost -v`。

4. **跨域执行与 `sideeffect` / `sidetest` 的关系**（2026-10-21 已查清，**不冲突**）。

   查清的结论：**副作用发生在父侧，不在子进程里**，故幂等保护挂在父侧即可，
   `ptc` **不需要**感知 `sideeffect`。

   实际链路（2026-10-21 核实 `ptc/subprocess.go` 与 `ptc/child.go`）：

   ```
   子进程程序 host.ping()
     → remoteCaller（子进程侧只是发请求的桩，Call 是远程桩）
       → 管道
         → 父侧 handler：判定环 → b.Call(ctx, args)   ← 副作用真正发生在这里
   ```

   ⇒ 宿主若要幂等保护，在**自己的 `Binding.Call` 实现里**接 `sideeffect.Runner`
   即可（`Binding.Call` 是宿主自己实现的函数，ptc 不管它的语义）。
   子进程里的重复调用最终都收敛到父侧那一次 `b.Call`，
   幂等键在那一层判，**天然覆盖子进程重跑**。

   这与「怎么说话」（跨进程通道）/「怎么去重」（幂等键）的分工一致：
   `ptc` 负责把请求送到父侧，`sideeffect` 负责保证父侧那次动作只施加一次。
   两者**零代码耦合**（`ptc` 不 import `sideeffect`），是**接线关系**。
5. **`ptc` 包头那句假话要改**（见第二节）：三闸不含内存。已在本轮修正为实情，
   并指向本档。
